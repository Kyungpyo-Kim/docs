줄이며 배운 것들

Lessons from Mitigating False Positives in Google's OSS-Fuzz-Gen

Paschal C. Amusuo · Dongge Liu · Ricardo Calvo · Jonathan Metzman · Oliver Chang · James C. Davis
Purdue University / Google · FSE Companion ’26, 2026년 7월 5–9일, 몬트리올 · 6쪽
정리·조회: 2026-10-21 · DOI / 원문

한눈에 읽기

AI가 만든 테스트에서 프로그램이 죽었다고 해서, 실제 사용 중에도 터지는 버그인 것은 아니다. 이 논문은 테스트를 만들 때 호출 조건을 챙기고, 크래시가 난 뒤에는 실제 진입점에서 재현 가능한지 다시 살피는 두 단계로 오탐을 줄인 경험을 다룬다.

1,555개평가 대상 함수 · 336개 프로젝트
57.3–65.2%기존에 Program Error로 분류된 크래시 중 검증기가 추가로 걸러낸 비율
약 9.3%기존 에이전트 대비 API 비용 증가

Abstract · 초록 원문 직접 인용

아래는 Paschal C. Amusuo, Dongge Liu, Ricardo Calvo, Jonathan Metzman, Oliver Chang, James C. Davis의 논문 원문 직접 인용이다. FSE Companion ’26 · DOI 10.1145/3803437.3805205. 원문 · CC BY 4.0. 번역·요약·생략 없이 옮겼으며 PDF 줄바꿈과 행 끝 분철만 읽기 좋게 정리했다. 기존 한국어 해설과 수치 검토는 별도 설명이다.

Fuzz testing is widely used in industry and open-source ecosystems, but its effectiveness depends on the quality of fuzz drivers that translate raw fuzzer input into valid function arguments. Automated fuzz driver generation reduces manual effort, but in practice often produces false positive crashes, especially for complex functions. We introduce OSS-Fuzz-Gen, an experimental system for agent-based fuzz driver generation. This paper reports our experience mitigating its false positives using two complementary strategies: constraint-based fuzz driver generation and context-aware crash validation against realistic program entry points. In our evaluation on 1,500 benchmark functions from OSS-Fuzz, these strategies filtered out more than half of crashes initially classified as program errors, at modest additional cost. We distill lessons for deploying LLM-based agents in large-scale fuzzing pipelines.

1. 왜 오탐이 생기나

퍼징은 입력을 계속 바꿔 넣으며 오류를 찾는 테스트다. 퍼즈 드라이버(하네스)는 그 바이트 입력을 대상 함수의 인자와 상태로 바꿔 준다. OSS-Fuzz-Gen은 LLM 에이전트로 드라이버를 작성하고 실행 결과를 받아 고치면서, 기존 테스트가 닿지 못한 함수까지 탐색한다.

문제는 내부 함수가 혼자 쓰이도록 만들어지지 않았다는 데 있다. 상위 호출자가 이미 길이를 검사했거나, 객체를 초기화했거나, 특정 순서로 API를 호출했다고 가정하는 경우가 많다. 생성한 드라이버가 이 절차를 건너뛰면 크래시는 실제로 발생해도 정상 호출 경로에서는 도달하지 못하는 상황일 수 있다.

저자들이 지적하는 오탐 원인은 입력 범위·구조 위반, 초기화 누락, 객체 불변식과 수명 위반, 전역 상태나 환경 조건 누락 등이다. 이런 보고가 쌓이면 유지보수자는 재현과 분류에 시간을 쓰고, 나중에는 진짜 버그 보고까지 덜 믿게 된다. [1, §2–3]

이 논문에서 오탐이란: 크래시 로그가 가짜라는 뜻이 아니다. 단독 함수 호출로는 발생하지만 프로젝트의 의도된 사용 경로에서는 실현 불가능한 크래시를 가리킨다. 다만 무엇을 의도된 진입점으로 잡느냐가 판정을 좌우한다.

2. 생성 전에 한 번, 보고 전에 한 번

제약 기반 드라이버 생성 — 잘못된 호출부터 줄이기

Constraint Generator는 대상 함수와 코드베이스의 호출 지점을 함께 읽는다. 인자 범위, 입력 구조, 객체 수명, 초기화, 호출 순서에서 반복되는 조건을 찾아 드라이버 작성·개선 에이전트에 전달한다. 완전한 명세를 증명하는 방식은 아니다. 저자들은 추론한 제약의 완전성이나 건전성을 보장하지 않는다고 밝힌다. 명백히 불가능한 호출을 줄이는 실용적인 지침에 가깝다. [1, §4.1]

문맥 기반 크래시 검증 — 실제 진입점에서 가능한지 확인하기

Crash Validator는 실행 후 남은 크래시를 검토한다. 기존 Crash Analyzer가 프로그램 오류로 분류한 결과도 다시 의심한다. 크래시 지점만 읽는 대신 공개 API나 외부 인터페이스에서 시작하는 호출 경로를 따라가며, 문제를 일으킨 인자와 상태가 실제로 만들어질 수 있는지 살핀다. [1, §4.2]

  1. 크래시가 난 함수와 위치를 찾는다.
  2. 크래시를 일으킨 입력 조건을 정리한다.
  3. 각 호출 지점에서 인자가 어떻게 만들어지는지 추적한다.
  4. 상위 호출자의 검사·제약이 크래시를 막는지 확인한다.
  5. 판정과 함께 코드 근거를 남긴다.

두 에이전트는 기존 코드 검색·컴파일·디버깅 도구, 빌드 산출물, 커버리지와 크래시 진단 자료를 활용한다. 별도의 정적 분석 체계를 새로 구축하기보다 기존 OSS-Fuzz-Gen 흐름에 연결했다. 구현에는 Google ADK를 사용했으며, 통합 과정은 7개 PR, 4,743줄 추가·986줄 삭제로 보고한다. [1, §4.3·5.1]

역할 분담: 생성 단계의 제약은 불필요한 크래시와 후속 분석을 줄인다. 사후 검증은 제약이 놓친 사례를 유지보수자에게 전달하기 전에 걸러낸다. 두 단계는 서로 대체하지 않는다.

3. 1바이트 버퍼가 만든 오해

논문의 Listing 1은 flexbuffers::GetRoot를 예로 든다. 이 함수는 버퍼 끝의 두 바이트를 읽는데, 생성 드라이버가 길이 1인 버퍼를 넘기면 heap-buffer-overflow read가 발생한다.

그런데 논문이 분석한 flatc 경로는 GetRoot 호출 전에 flexbuffers::VerifyBuffer를 실행한다. 이 검증은 최소 3바이트를 요구하므로, 해당 경로에서는 문제의 1바이트 입력이 대상 함수까지 도달하지 못한다. 검증기는 이 근거로 크래시를 오탐으로 판정했다. [1, Listing 1]

이 사례가 모든 외부 호출자의 안전성을 증명하는 것은 아니다. 다른 공개 API나 다른 호출 경로가 있다면 별도 확인이 필요하다. 이는 사례를 실무에 적용할 때의 해석이다.

논문은 API 비용 증가를 약 9.3%로 보고한다. 평가 조건은 함수당 10회 병렬 시도, 1,555개 함수, 336개 프로젝트이며 전체 비용은 $14,616이다. $0.939는 새 에이전트의 추가 비용만이 아니라 기존 에이전트를 포함한 전체 비용이다. 장기간 퍼징 실행 비용이나 사람의 분류 시간을 모두 합친 총소유비용으로 해석하면 안 된다. [1, 표 4]

5. 검증 에이전트도 검증해야 한다

사람이 살펴본 분석 20건 중 신뢰할 만한 결론은 11건(55%)이었다. 오탐 판정군에서는 10건 중 6건, 실제 버그 판정군에서는 10건 중 5건이었다. 저자들은 실제 결함으로 본 5건을 유지보수자에게 제보했다고 적었다. 이 수치는 패치 완료나 보안 취약점 확정 건수가 아니다. [1, §5.2·표 3]

  • 크래시 위치를 잘못 찾음: 5건
  • 호출 지점을 충분히 살피지 않음: 2건
  • 근본 원인을 잘못 식별함: 1건
  • 제약·도달 가능성 분석 오류: 1건

위치 식별 오류 5건 중 4건은 앞 단계 에이전트의 잘못된 근본 원인 분석에서 시작됐다. 뒤에 검증 에이전트를 하나 붙이는 것만으로는 독립적인 검증이 되지 않을 수 있다. 잘못된 전제를 그대로 물려받으면 같은 방향으로 틀린다.

근거의 한계: 이 논문은 산업 경험 보고서다. 소규모 수동 검토만으로 전체 시스템의 정확도·재현율, 모든 실제 버그의 보존, 다른 모델·프로젝트에서의 같은 성과를 보장하지 않는다. 이 정리는 논문 전체를 읽고 수치를 옮긴 것이며, 평가 코드를 재실행하거나 데이터셋의 정답을 독립 검증하지는 않았다.

원문 표기 차이: 초록은 약 1,500개 함수를 언급하지만 본문·표의 정확한 합계는 1,555개다. 도입부의 “최대 64%”와 달리 표 2·§5.2는 최대 65.2%를 제시한다. 본 정리는 상세 표를 우선했다. 표 1 Total 행의 15.0%는 세트별 감소율을 합친 값으로 보이며 전체 감소율로 해석하지 않았다. 커버리지 합계도 전체 가중 평균으로 사용하지 않았다.

6. 저자들이 남긴 다섯 교훈

  1. 제약은 잡음을 줄이지만 충분하지 않다. 보조 함수나 복잡한 조건까지 모두 다루기는 어렵다.
  2. 전체 프로그램 문맥이 크래시 분류를 개선한다. 실제 진입점에서 가능한 경로인지 살피는 쪽이 유지보수자에게 전달되는 오탐을 크게 줄였다.
  3. 에이전트 신뢰성은 앞 단계 정보의 품질에 달렸다. 근본 원인 분석의 오류가 뒤 단계로 전달된다.
  4. 추가 비용은 배포 가능한 수준이었다. 논문 평가에서 API 비용 증가가 10% 미만이었으며 지속적인 퍼징에 분산할 수 있었다.
  5. 새 기법만큼 에이전트 간 연결이 중요하다. 공유 문맥, 단계 간 협력, 실제 실행 경로 검증을 더 촘촘하게 만드는 방향을 제안한다. [1, §6]

7. 실무에 가져온다면

아래는 논문 결과에서 도출한 적용 제안이다. 논문에서 구현·평가한 추가 기능으로 읽지 말 것.

AI 테스트 자동화의 성과를 크래시 수 하나로 평가하지 않는 편이 좋다. 유효한 드라이버 비율, 도달한 코드, 사람이 확인한 실제 결함, 보고당 분류 시간, 잘못 제외한 실제 결함을 나눠 추적하면 테스트 생성과 보고 품질을 함께 볼 수 있다.

검증기에는 앞 에이전트의 요약뿐 아니라 원본 크래시 로그, 스택, 입력, 재현 코드와 호출 지점을 함께 주는 것이 좋다. 불가능하다는 판정에는 입력 검사가 위치한 코드와 해당 검사에서 크래시 지점까지의 경로를 요구하고, 근거가 약하면 자동 폐기하지 않고 사람 검토로 넘기는 운영이 안전하다.

RTL·실리콘 검증에도 비슷한 질문을 적용할 수 있다. 테스트벤치가 reset·핸드셰이크·설정 순서 등 환경 계약을 지켰는지, 실패 상태가 실제 상위 모듈에서 도달 가능한지를 나눠 보는 것이다. 다만 소프트웨어 퍼징의 57.3–65.2% 수치를 하드웨어 검증 성능으로 옮길 근거는 이 논문에 없다.

읽고 남길 한 문장: 자동으로 실패를 찾는 능력과, 그 실패가 실제 제품의 문제인지 설명하는 능력을 별도로 설계하고 평가하자.

8 Conclusion · 결론 원문 직접 인용

아래는 Paschal C. Amusuo, Dongge Liu, Ricardo Calvo, Jonathan Metzman, Oliver Chang, James C. Davis의 논문 원문 직접 인용이다. FSE Companion ’26 · DOI 10.1145/3803437.3805205. 원문 · CC BY 4.0. 번역·요약·생략 없이 옮겼으며 PDF 줄바꿈과 행 끝 분철만 읽기 좋게 정리했다. 기존 한국어 해설과 수치 검토는 별도 설명이다.

Our goal is to make automated fuzz driver generation more usable by reducing false positive crashes. In OSS-Fuzz-Gen, a function-level fuzzing strategy expands coverage but also produces many crashes that are infeasible in real executions, increasing triage costs. We reported on mitigating false positives by combining lightweight constraints during driver generation with context-aware crash validation against project entry points. We learned that constraints reduce noise but do not eliminate false positives, whole-program context substantially benefits crash triage, and the costs of an agentic approach are modest enough to support practical deployment.
