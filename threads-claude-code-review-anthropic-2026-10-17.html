Claude Code 팀은 코드 리뷰를 어떻게 바꾸었나

코드 생산량이 급증해도 품질을 지키는 방법은 모든 줄을 사람이 읽는 것이 아니라, 변경마다 맞는 검사를 배치하고 되돌림을 빠르게 하는 것이다.

원문: Anthropic, “How the Claude Code team does code review” · 2026-10-15 · 약 14분 읽기

한눈에 보기

리뷰를 없앤 게 아니라, 사람의 검토 시간을 줄이면서 되돌림이나 장애가 늘지 않도록 설계를 바꿨다. Claude는 작성 중 검증과 PR 리뷰를 맡고, 자동 보안·CI 검사와 위험도별 승인이 뒤따른다. 배포 후에도 문제를 빨리 찾아 되돌릴 수 있게 한다.

모두 Anthropic 공식 글이 서술한 수치다. 회사가 소개한 내부 운영 성과이며, 글은 외부 독립 검증을 제시하지 않는다. 글은 또한 Anthropic 모노레포의 일일 변경량이 5월 약 2,500건에서 9월 3만 건 초과로 늘었다고 설명한다. Claude Code 저장소는 별도 저장소다.

실제 운영 절차: PR 생성부터 롤백까지

원문의 흐름도와 단계별 설명을 기준으로 실제 처리 순서를 다시 그렸습니다. PR 전 검증이 먼저이고, PR이 열리면 CI·AI 리뷰·보안 리뷰가 필수 점검으로 붙습니다. 세 점검의 실행 순서를 특정하거나 동시에 실행된다고 단정하지 않으며, 지적이 해결되고 검사가 통과한 뒤에만 변경 위험에 맞는 사람 승인을 거쳐 머지 큐로 갑니다.

공식 원문의 Figure A와 단계별 절차를 다시 그린 운영 흐름. 위험도별 승인, 커밋별 재승인, 검사 실패 시 되돌아가는 경로를 추가했다. 원문이 제시한 현재 운용 방식이며, 지표 악화 때 자동으로 승인을 조이는 회로는 아직 없다고 명시한다.

왜 리뷰의 기준을 바꿨나

에이전트가 만드는 변경이 빠르게 늘면 사람이 모든 줄을 하나씩 읽는 방식은 병목이 된다. Anthropic 팀은 “사람이 코드를 읽었는가?”보다 “무엇이 잘못될 수 있고, 그 문제를 자동 검사와 사람이 각각 어떻게 잡아야 하는가?”를 묻는다.

코드 리뷰에는 두 가지 목적이 있다. 문제가 사용자에게 도달하기 전에 찾아 고치는 것, 그리고 팀이 코드와 시스템을 함께 이해하는 것이다. 공식 글은 첫 번째 목적에 초점을 둔다가 뒤에서 두 번째 목적도 다룬다.

사람의 비용도 리뷰 시간만으로 계산하지 않는다. 리뷰를 줄이는 대신 나쁜 코드가 만든 장애·수정 작업이 늘면 절약이 아니다. 그래서 팀은 PR당 사람 승인 수(중앙값·95퍼센타일), 사람 댓글 수, 사람을 기다린 시간을 추적하고, 되돌림과 장애율을 안전 기준으로 둔다. 목표는 Claude Code 저장소의 대부분 PR을 사람 한 명 이하(작성자 자신도 포함)로 머지하되 되돌림·장애를 늘리지 않는 것이다.

각 점검층의 작동 방식

1. PR을 열기 전: 실행 가능한 증거를 만든다

Claude에게 테스트·빌드·디자인과 비교할 스크린샷처럼 직접 실행해 확인할 수단을 준다. “끝났다”는 말 대신 결과를 보여 달라고 하고, 별도 컨텍스트의 하위 에이전트가 diff를 확인한다. 팀원들은 버그 탐색, diff 단순화, 실제 동작 점검용 내부 스킬도 활용한다. 반복 지적은 프롬프트에 쌓기보다 린트 규칙·스킬·프로젝트 안내를 고쳐 원인에서 해결한다.

  • CLAUDE.md: 기술 스택, 관례, 목표·비목표를 알려주는 짧은 안내서. 큰 저장소에서는 세부 문서로 연결한다.
  • REVIEW.md: 코드 소유자가 해당 영역에서 중요한 실패 유형, 제외 경로, 근거가 될 파일·줄, 사소한 지적의 한도를 적는다.

글은 Claude Code 제작자 Boris Cherny의 설명을 인용한다. 검증 방법은 영역에 따라 셸 명령, 테스트, 브라우저나 모바일 시뮬레이터 실행 등이 될 수 있고, 검증 수단을 주면 결과가 두세 배 좋아진다는 그의 추정도 소개한다.

2. 모든 PR: AI 리뷰와 발견 사항 검증

Claude가 변경사항을 저장소 전체와 PR의 의도에 비춰 읽고, 버그 수정이면 근본 원인을 확인한다. 여러 에이전트가 버그를 찾고 별도 에이전트 그룹이 각 발견에 투표한다. 충분히 타당한 것만 남기고 스타일·진단·정리 지적은 걸러낸다. 남은 코멘트에는 심각도와 Important, Nit, Pre-existing 같은 라벨을 붙인다.

지적은 수정하거나 이유를 남겨 해결해야 한다. 나중 커밋에서 문제가 실제로 고쳐지면 해당 지적은 자동으로 정리될 수 있다. 원문은 Code Review 연구 프리뷰 때 실질적인 리뷰 댓글을 받은 내부 PR 비중이 16%에서 54%로 늘었다고 보고한다. 1,000줄이 넘는 PR 대부분에서는 발견 사항이 나오고, 작은 PR 대부분은 깨끗하게 통과한다고 설명한다. 저장소별로 Quick·Standard·Deep 검토 수준을 설정할 수 있으며, 놓친 버그의 비용이 큰 영역에서는 Deep이 적합하다고 한다.

3–4. 보안과 CI: 통과하지 못하면 머지하지 않는다

보안 리뷰는 별도의 자동 점검이다. 버그 리뷰나 보안 리뷰에 미해결 지적이 있으면 머지할 수 없다. 오탐이면 간단한 이유를 남겨 닫는다. 린트, 타입 검사, 각 플랫폼 테스트, 빌드도 차단 조건이다. 일반적인 CLI PR은 수십 개의 검사를 실행할 수 있다. PR 템플릿은 테스트 방법과 되돌리는 법을 묻고, Claude가 초안을 채워도 변경을 요청한 사람이 확인한다.

5. 사람 승인: 위험은 변경 자체로 판단한다

위험예시사람 승인
낮음문서·문구 수정, 내부 전용 기능, 플래그 뒤의 추가 기능자동 리뷰·보안 검사가 통과하면 승인 생략 가능
보통일반 제품 변경, 캐시·자동 업데이트·시스템 프롬프트 등 민감 영역1명
높음가장 위험한 코드 및 항상 2인이 필요한 일부 경로2명
  • 작성자가 등급을 고르는 게 아니라 분류기가 변경 내용을 읽고 정한다. 두 번째 분류기가 추가 사람 검토가 필요한지 다시 확인한다.
  • 민감 경로와 CI 워크플로 파일은 항상 사람 검토가 필요하다. 가벼운 승인 경로는 신뢰된 작성자에게만 제공하며, 그 밖의 작성자는 추가 승인이 필요하다.
  • 에이전트 승인은 사람 승인으로 계산하지 않는다. 에이전트에게 변경을 지시한 사람은 필요한 리뷰어 한 자리를 맡는다.
  • 승인은 특정 커밋을 대상으로 한다. 에이전트가 새 커밋을 푸시하거나 병합 충돌을 수동으로 해결해 시스템이 검증할 수 없으면 승인을 다시 받아야 한다.

6–7. 머지 이후: 점진 배포하고 되돌릴 준비를 한다

머지 큐는 변경을 최신 main에 적용한 상태에서 모든 검사를 다시 실행한다. PR 둘이 각각 통과해도 합쳐졌을 때 깨질 수 있기 때문이다. 새 기능은 대개 플래그로 감춰 사내에서 먼저 쓰고, 공개 배포는 latest 채널에 먼저 나간 뒤 stable 채널로 이동한다. 문제는 플래그를 끄거나 되돌려 빠르게 복구할 수 있다. 주간 온콜과 사고 리뷰는 문제를 어느 층에서 잡았어야 했는지 되짚는다.

아직 남은 빈틈: 원문에 따르면 나쁜 머지 감지는 작성자·온콜과 되돌림·장애 대시보드에 의존한다. 지표가 악화되면 승인 조건을 자동으로 강화하는 차단 장치(circuit breaker)는 아직 없으며, 팀 엔지니어들도 사람 없는 머지를 늘리기 전에 이를 원한다고 한다.

리뷰어도 테스트하고, 반복을 멈추게 한다

실제 사고로 평가 세트를 만든다

사고를 일으킨 과거 PR과 후속 수정·되돌림을 모으고, 해당 코드를 아는 엔지니어가 버그와 위치를 확인한다. 리뷰어는 이 평가 세트를 매일 실행하며, 프롬프트·도구·모델을 바꿀 때 점수를 비교한다. 실제 버그를 잡는 성능이 나아지면 채택하고 아니면 되돌린다. 새 사고가 생길 때마다 평가 문제가 추가된다.

불필요한 지적도 측정한다

PR 참여자가 지적을 고쳤는지, 틀렸다고 했는지, 의도한 동작이라 설명했는지, 중요하지 않아 넘겼는지를 살펴본다. 문제가 없다고 확인된 PR에 리뷰어를 적용해 해로운 수정으로 이어질 지적도 센다. 우선순위는 실제 버그를 잡는 것이 먼저, 리뷰 왕복을 줄이는 것이 그다음이다.

리뷰가 끝없이 돌지 않게 한다

사람은 사소한 지적을 곧바로 넘길 수 있지만 에이전트는 매번 고쳐 커밋과 리뷰를 추가로 만들 수 있다. 원문은 한 CLI PR이 밤새 50회가 넘는 리뷰·수정을 거친 사례를 든다. 반복 지적된 코드의 약 59%는 첫 리뷰 때부터 있던 코드였다. 새로운 버그가 아니라 기존 문제를 매 차례 조금씩 더 찾은 셈이다.

이에 따라 세 차례 리뷰 뒤에는 접근법을 다시 생각하게 하고, 초반 이후에는 새 diff 중심으로 재검토한다. 같은 유형의 버그를 한꺼번에 묶고, 이미 남긴 지적은 반복하지 않는다. 기존 코드에서도 놓친 버그를 찾도록 야간 리뷰도 돌린다. 원문은 이런 수렴 개선 뒤 한 번에 통과한 PR이 65%에서 78%로 늘고, 다섯 차례를 초과한 PR은 8.9%에서 1.5%로 줄었다고 보고한다.

사람은 무엇에 집중하나

  • 무엇을 만들지: 방향·제품 감각·범위 판단. 리뷰 병목을 해결한 팀도 외부 팀의 변경은 사람이 검토하며 “이걸 만들 필요가 있나?”를 묻는다.
  • 고위험 코드: 결제, 자동 업데이트, CI처럼 실수의 영향이 큰 영역.
  • 아키텍처: 다른 개발자가 따라 하게 될 구조와 패턴.
  • 검증 증거: 테스트 출력·실행 명령·스크린샷·리뷰 결과를 보고 검사가 놓칠 일을 판단한다. 증거가 부족하면 성급히 승인하지 말고 정식 리뷰를 요청한다.
  • 결과에 대한 책임: 코드를 직접 썼는지와 무관하게 사람은 자신이 배포를 요청한 변경을 책임진다.

사람이 모든 코드의 전체 구조를 머릿속에 넣어둘 필요는 없다는 것이 팀의 관점이다. 이해가 필요한 시점에 Claude에게 특정 모듈 설명을 만들게 하거나, 학습자가 선호하는 방식의 작은 시각화 자료를 만든다. 사소한 diff를 줄마다 읽는 것보다 곧 바꿀 모듈을 집중적으로 이해하는 편이 효과적이다.

“배포한 사람이 맡는다”는 책임 원칙

작거나 중간 규모의 변경에서 문제가 생기면 보통 그 변경을 올린 사람이 수정한다. 다만 책임을 개인 탓으로 돌리는 뜻은 아니다. 작은 변경, 기능 플래그와 되돌리기, 위험에 맞춘 검사·인력, 빠른 텔레메트리와 내부 사용이 문제의 영향 범위를 줄인다. 사고 리뷰는 개인 비난보다 시스템의 어느 점검층을 보완할지 묻는다.

열린 채널에서 작업을 공유해 소유자가 아닌 동료도 빈틈을 발견하고 의견을 보탠다. 에이전트로 시작하는 일이 쉬워진 만큼, 방향이 어긋난 PR은 완성된 뒤 막기보다 초기에 더 단순한 방법이나 이전 결정을 알려 조정한다. 작성 비용이 낮으면 PR을 닫거나 다시 설계하는 것도 손실로 느껴지지 않는다.

다른 팀에서 시작하는 방법

  1. PR 전: 에이전트가 실행할 검사 목록을 짧은 CLAUDE.md에 적고 포맷터·린터 훅을 둔다. 로컬 /code-review·/security-review 또는 새 컨텍스트의 하위 에이전트 검토를 사용한다. 반복 피드백은 REVIEW.md로 옮긴다.
  2. PR 단계: CI 통과를 필수로 하고 템플릿에 테스트·위험·되돌리는 방법을 적는다. AI 리뷰와 보안 리뷰를 저장소 하나에서 시작해 수 주간 다듬은 뒤 확대한다. 모든 리뷰 스레드는 해결돼야 머지되게 한다.
  3. 검토 깊이: 놓친 버그의 비용에 따라 빠른 검토와 심층 검토를 구분한다. 리뷰 왕복 횟수를 제한하고 몇 차례 이후에는 새 diff만 본다.
  4. 승인: 작성자가 아닌 변경 위험으로 등급을 정한다. 엄격하게 시작하고 근거가 쌓이면 완화한다. 인증·결제·CI·릴리스·설치 경로에는 CODEOWNERS와 브랜치 보호로 사람 승인을 유지한다. 새 커밋이 생기면 이전 승인을 무효화하고, 봇 승인이 사람 자리를 대신하지 못하게 한다.
  5. 배포와 학습: 머지 큐, 기능 플래그, 내부 선행 사용, 단계적 배포, 빠른 롤백을 준비한다. 사고와 되돌림을 평가 세트에 넣고, 리뷰 시스템을 바꿀 때마다 재평가한다. 사람의 시간 절감과 함께 되돌림·장애율을 계속 본다.
핵심 순서: 먼저 에이전트가 스스로 실행하고 결과를 증명할 수 있는 검사를 마련한다. 그다음 작은 범위에서 AI 리뷰를 평가한다. 낮은 위험 변경의 사람 승인 생략은 지표와 책임 체계가 준비된 뒤에 검토한다.

Threads의 수치, 원문과 대조

Threads의 주요 성과 수치 대부분은 링크된 공식 글 본문에서 확인된다. 단, 회사가 공개한 내부 지표이므로 외부 독립 감사 결과로 해석하면 안 된다. 보조로 든 공개 이슈 통계는 GitHub 이슈 저장소를 수집한 제3자 일일 집계와 대조했고, 정확한 원시 검색 쿼리·시점이 공개되지 않은 값은 확인 한계를 표시했다.

“6월보다 처리 속도가 빨라졌다”제3자 타임라인의 닫힌 이슈 집계는 6월 7,827건, 9월 8,820건이다. 닫힌 건수는 늘었지만 이 수치만으로 처리 속도(예: 중앙 해결 시간)가 빨라졌다고 단정할 수는 없다. 신규·종료의 월간 흐름만 보여 주는 참고치.
요약: 핵심 리뷰 성과와 대부분의 수치는 공식 원문에서 확인된다. Threads의 공개 GitHub 이슈 카운트는 제3자 집계와 대체로 가까우나 완전히 일치하지 않는다. 특히 “열린 이슈 14,471”은 하루 차이의 별도 스냅샷으로 남겨 두고, 확인된 단일 기준값처럼 쓰지 않았다.

공식 수치도 내부 운영 자료로 소개된 회사의 자체 보고이며 외부 독립 검증은 아니다. 제3자 tracker는 GitHub 공개 이슈를 일별 수집한다고 밝히지만, 시점이 지난 뒤 재집계될 수 있다. 수치 비교는 각 출처의 집계 시점과 지표 정의를 함께 봐야 한다.
