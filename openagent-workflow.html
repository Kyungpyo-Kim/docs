Prompt Engineering / OpenCode / Oh My OpenAgent

장시간 AI 빌드 워크플로우 재현 가이드

Anshu의 24시간 Claude 게임 제작 사례를 분석해, opencode와 oh-my-openagent 환경에서 재현 가능한 실행 구조와 프롬프트 템플릿으로 정리했다.

핵심 결론

이 사례는 단일 프롬프트의 성과가 아니라 장기 goal runner, 병렬 agent, 시각 검증, 엄격한 judge, Blender MCP, 반복 개선 루프를 결합한 에이전트 운영 패턴이다.

opencode에서도 재현 가능하다. 다만 Claude Code 사례를 그대로 복제하는 것이 아니라, oh-my-openagent의 Sisyphus, ultrawork, /goal, Team Mode, Playwright, Blender MCP, Firecrawl을 조합해 같은 실행 원리를 구현하는 방식이 적합하다.

원본 사례의 구조

1. 품질 기준 중심 프롬프트

“우주 게임을 만들어라”가 아니라 AAA급, 포토리얼, 압도적 비주얼, low-poly 금지처럼 결과물의 기준을 강하게 설정했다.

2. 자율 실행

질문하지 말고 직접 결정하고, 구현하고, 브라우저에서 확인하고, 부족하면 계속 고치라는 실행 규칙을 넣었다.

3. 검증 루프

스크린샷을 찍고 AAA 게임과 비교한 뒤, judge가 통과시키기 전까지 시각 품질과 사용성을 반복 개선했다.

추가로 들어간 실행 장치

  • Blender MCP로 모델링 도구 접근을 제공했다.
  • 별도 judge subagent가 냉정하게 시각 품질을 평가했다.
  • 장시간 실행 중에도 사람이 가끔 방향을 조정했다.
  • 학습한 모델링 노하우를 skill로 저장해 다음 asset 제작에 재사용했다.

oh-my-openagent 기준 구성

Sisyphus

전체 목표를 잡고 specialist agent를 배치하는 lead orchestrator 역할.

ultrawork / ulw

짧은 응답이 아니라 완료까지 밀어붙이는 장기 실행 모드.

/goal

세션 목표를 유지하고 idle마다 continuation prompt를 재주입하는 goal runner.

Team Mode

lead agent와 여러 specialist를 병렬로 실행하는 구조.

Playwright MCP

브라우저 실행, 스크린샷, 콘솔 에러, 실제 UI 검증 담당.

Blender MCP

프롬프트만으로 어려운 3D asset 제작을 실제 도구 조작으로 보완.

기본 실행 템플릿

oh-my-openagent의 Sisyphus에게 장기 작업을 맡길 때 쓰는 범용 템플릿이다.

ultrawork

You are Sisyphus, the lead orchestrator in oh-my-openagent.
Run this as a long autonomous build, not as a short prototype task.

Objective:
Build a complete [PROJECT_TYPE] that reaches [QUALITY_BAR].
The result must feel production-grade, polished, and visually impressive.
It must not feel like a quick demo, template, placeholder, or low-effort AI output.

Target:
- Project: [PROJECT_NAME]
- Domain: [GAME / APP / TOOL / WEBSITE]
- Stack: [STACK]
- Allowed libraries: [ALLOWED_LIBRARIES]
- Forbidden: [FORBIDDEN_ASSETS_OR_SHORTCUTS]
- User experience target: [WHAT_THE_USER_SHOULD_FEEL_OR_DO]
- References to match or exceed: [REFERENCE_PRODUCTS / GAMES / SITES]

Operating mode:
- Do not stop after the first working version.
- Do not ask clarification questions unless blocked by credentials, missing local tools, or irreversible external action.
- Make strong product, design, architecture, and implementation decisions yourself.
- Use specialist agents aggressively when useful.
- Keep the main context lean by delegating research, visual critique, asset planning, code review, and debugging.
- Continue until the success criteria are met or a real blocker is proven with evidence.

Required team roles:
- Explorer: inspect repo, dependencies, runtime, and constraints.
- Researcher / Librarian: gather references, implementation patterns, and relevant docs.
- Designer / Visual Engineering: define visual direction, UI, motion, layout, and polish bar.
- Builder / Hephaestus: implement end-to-end.
- Visual Judge: compare screenshots against references and return PASS/FAIL only.
- Reviewer: check code quality, bugs, performance, and missing verification.

Workflow:
1. Inspect the repository and environment.
2. Create a concise implementation plan with milestones.
3. Build the smallest complete vertical slice.
4. Run it locally.
5. Use browser automation / Playwright to inspect the actual result.
6. Capture screenshots for all key states.
7. Ask the Visual Judge to critique screenshots against the reference bar.
8. Fix the highest-impact issues.
9. Repeat visual, UX, performance, and code-quality passes.
10. Do not mark complete until the verifier says the result satisfies the success criteria.

Success criteria:
- [SUCCESS_CRITERION_1]
- [SUCCESS_CRITERION_2]
- [SUCCESS_CRITERION_3]
- Runs locally with documented commands.
- No blocking console/runtime errors.
- Key flows are tested manually or with automation.
- Screenshots prove the visual result.
- Final answer includes what was built, how to run it, what was verified, and any remaining limits.

Completion rule:
You may only finish when you can provide evidence. If you cannot verify something,
say exactly what blocked verification and keep working on what can be improved.

Three.js 우주 게임 템플릿

Anshu식 사례를 opencode + oh-my-openagent에서 재현할 때 쓰는 실전 버전이다.

ultrawork

You are Sisyphus, the lead orchestrator in oh-my-openagent.
Run this as a long autonomous build with aggressive parallel delegation.

Objective:
Build a complete browser-based space exploration game using Three.js.
The game must look cinematic, atmospheric, premium, and as close as possible to AAA space games or high-end space photography.
It must not look low-poly, plasticky, blocky, generic, empty, or like a student demo.

Hard constraints:
- Use Three.js as the core rendering stack.
- Do not use external art packs, downloaded models, copied game templates, or stock assets.
- Generate visuals procedurally or create assets through Blender MCP if available.
- Build the ship, planets, UI, audio, shaders, menus, story fragments, and game loop yourself.
- Keep the game playable in a browser.

Player fantasy:
The player is the pilot of a deep-space survey vessel exploring a vast unknown region.
They can fly through space, inspect the cockpit, discover planets, scan anomalies,
approach derelict ships or stations, use a star map, and uncover a larger mystery through exploration.

Core loop:
Fly - discover - scan - learn - unlock - choose the next destination.

Required experience:
- Smooth ship flight.
- Cinematic cockpit or ship-view presentation.
- Procedural starfield, planets, nebulae, distant objects, and discoveries.
- Star map or navigation interface.
- Scanning / discovery mechanic.
- Environmental story fragments.
- HUD and menus that feel designed, not placeholder.
- Sound or generated ambience if possible.
- Strong lighting, atmosphere, post-processing, scale, and motion.

Team delegation:
- Send Researcher to gather references from Starfield, Elite Dangerous, No Man's Sky, and cinematic space photography.
- Send Visual Engineering to define the look: lighting, shaders, color, HUD, motion, camera, post-processing.
- Send Builder / Hephaestus to implement the playable game.
- Send Visual Judge to review screenshots with a strict PASS/FAIL standard.
- If Blender MCP is available, send Asset Modeler to create the player ship, cockpit controls, probes, derelicts, stations, and props.
- Send Reviewer to check architecture, runtime errors, performance, and missing tests.

Verification loop:
1. Run the game locally.
2. Open it with browser automation / Playwright.
3. Capture screenshots of cockpit or ship flight, planet approach, star map, discovery/anomaly moment, and menu/HUD state.
4. Give screenshots to Visual Judge.
5. Visual Judge must return PASS or FAIL, top 10 problems, and top 5 fixes.
6. If FAIL, improve the game and repeat.
7. Do not complete until screenshots show a premium result and the game is playable end-to-end.

Performance target:
- Aim for smooth 60fps.
- Use LOD, instancing, dynamic resolution, post-processing discipline, and shader optimization.
- Fix console errors, rendering artifacts, z-fighting, broken controls, layout overlap, and loading failures.

Completion rule:
Do not say done because the code compiles. Only finish when browser screenshots,
interaction, and reviewer evidence support completion. If a tool is unavailable,
document the exact limitation and continue with the best available substitute.

/goal 짧은 버전

먼저 짧게 검증할 때는 아래처럼 시작하는 편이 안전하다.

/goal "Build a 20-minute vertical slice of the Three.js space exploration game with browser screenshots and visual judge review." --max-turns 12 --max-minutes 20 --success "playable flight; one planet approach; one discovery moment; screenshots captured; no blocking runtime errors"

검증이 성공하면 아래처럼 장시간 goal로 확장한다.

/goal "Build a complete Three.js space exploration game using the oh-my-openagent workflow. Use Sisyphus as orchestrator, delegate research, visual engineering, implementation, visual judging, and review. Keep iterating with browser screenshots until the result is playable, visually premium, and free of blocking runtime errors." --max-turns 80 --max-minutes 1440 --max-tokens 2000000 --success "playable end-to-end; browser verified; key screenshots captured; visual judge passes or remaining gaps are explicitly evidenced; no blocking console errors" --constraints "no external art packs or copied game templates; use procedural assets or Blender MCP-generated assets; do not stop at prototype quality"

Specialist Prompts

Visual Judge

You are the Visual Judge.
Your job is to be strict, impartial, and concrete.

Compare the current browser screenshots against these references:
- Starfield
- Elite Dangerous
- No Man's Sky
- cinematic NASA/ESA space photography
- premium sci-fi cockpit UI references

Do not praise effort.
Do not accept prototype quality.
Do not lower the bar.

Evaluate:
- composition
- lighting
- atmosphere
- materials
- geometry quality
- shader quality
- post-processing
- UI/HUD polish
- motion readability
- scale
- visual artifacts
- performance clues
- whether the result feels premium or obviously generated

Return exactly:
PASS or FAIL
Top 10 concrete problems
Top 5 highest-impact fixes
What must be improved before completion

Asset Modeler / Blender MCP

You are the Asset Modeler.
Use Blender MCP if available.

Create intentional hard-surface 3D assets for the game:
- player ship
- cockpit controls
- scanner device
- derelict station pieces
- probes
- landing props
- distant megastructure silhouettes

For each asset:
- prioritize readable silhouette
- add material separation
- avoid blocky placeholder geometry
- export/import into the Three.js pipeline
- verify the asset in the actual browser scene
- write reusable lessons into project notes or a local skill file

If Blender MCP is unavailable, design the closest procedural Three.js substitute and clearly report the limitation.

Researcher

You are the Researcher.
Use Firecrawl/web search for reference and implementation research.

Find concise, high-signal references for:
- Three.js space rendering
- procedural planets
- starfields and nebulae
- atmospheric scattering
- cockpit HUD design
- WebGL performance optimization
- screenshot-based visual QA workflows

Return only implementation-relevant findings with source links. Do not produce a long report unless asked.

프롬프트만으로 안 되는 부분

텍스트 프롬프트는 방향을 정하지만, 장시간 실행과 고품질 결과는 실행 환경이 만든다.
  • 24시간 자동 실행은 모델 능력이 아니라 goal runner, tmux, session recovery 같은 런타임 기능이다.
  • Blender 수준의 3D asset은 프롬프트만으로 생기지 않는다. Blender MCP나 동등한 도구 접근이 필요하다.
  • AAA급 비주얼은 선언만으로 보장되지 않는다. 브라우저 스크린샷, judge, 성능 측정, 반복 수정이 필요하다.
  • 모델은 실제 화면이 깨졌어도 완료라고 말할 수 있다. 따라서 Playwright나 브라우저 기반 검증이 핵심이다.
  • 외부 asset을 금지하면 shader, procedural mesh, UI, audio까지 직접 만들어야 하므로 시간과 비용이 커진다.

권장 실행 순서

  1. oh-my-openagent를 별도 테스트 repo 또는 테스트 opencode profile에 설치한다.
  2. Firecrawl, Playwright MCP, Blender MCP 연결을 각각 짧게 검증한다.
  3. 20분 vertical slice goal로 자동 continue와 judge 루프가 실제로 도는지 확인한다.
  4. 성공하면 6시간 goal로 확장한다.
  5. 마지막에 24시간 goal로 늘리고 tmux/systemd로 세션 생존성을 확보한다.
